## 1. ما الذي قمنا بفعله بالتحديد؟

قمنا بربط واجهة المستخدم المبنية بواسطة مكتبة **React 19** وأداة البناء **Vite** بنظام الباك إند المعياري المبني بواسطة **ASP.NET Core** (معمارية Modular Monolith مع خدمات Microservices داعمة مثل المستودع عبر Java gRPC).

تم نقل التطبيق من طور البيانات الوهمية (Mock Data) إلى طور الاتصال الفعلي بالـ REST APIs الحقيقية، مع تحقيق ما يلي:
* تفعيل طبقة اتصال شبكي مركزية تعتمد على مكتبة **Axios** مع إعداد اعتراض الطلبات والاستجابات (**Interceptors**).
* حقن رمز الدخول الموثق (**JWT Bearer Token**) تلقائياً في ترويسات كافة الطلبات المحمية.
* مطابقة نماذج نقل البيانات (**DTOs - Data Transfer Objects**) بين لغة C# في الباك إند ولغة JavaScript في الواجهة، ومعالجة فروقات التسميات (مثل PascalCase مقابل camelCase).
* تفعيل التراجع الآمن وإدارة الحالات الثلاث لكل واجهة: التحميل (**Loading State**)، والخطأ (**Error State**)، والنجاح (**Success State**).
* إتاحة التبديل السهل بين البيانات الحقيقية والبيانات التجريبية عبر متغير بيئي واحد (`VITE_USE_MOCK`) لتسهيل العمل دون اتصال بالإنترنت عند الحاجة.

## 3. كيف يتواصل تطبيق React مع الـ Backend؟

تعتمد الواجهة الأمامية على **نمط المعمارية الطبقية (Layered Architecture)** لضمان الفصل التام للمسؤوليات (**Separation of Concerns**):

```
+-------------------------------------------------------------+
|             صفحات ومكونات الواجهة (UI Components)            |
|  LoginPage, ProductsPage, CheckoutPage, OrdersPage, ...    |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|               سياقات إدارة الحالة (Context API)              |
|        AuthContext (المستخدم والتوكن) - StoreContext (السلة)       |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|            طبقة المحول والخدمات (storeApi.js)                |
|  - تحويل DTOs القادمة من السيرفر إلى خصائص تفهمها الواجهة    |
|  - التعامل مع الحالات الخاصة (Casing, IDs, Missing Fields)    |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|            عميل الشبكة المركزي (api.js - Axios)             |
|  - Request Interceptor: يضيف Bearer Token تلقائياً          |
|  - Response Interceptor: يلتقط الأخطاء الموحدة 401, 404...  |
+-------------------------------------------------------------+
                              |
                              v  (Vite Reverse Proxy: /api -> http://localhost:5097)
+-------------------------------------------------------------+
|            خادم الباك إند (ASP.NET Core Web API)            |
|       UsersModule | ProductsModule | OrdersModule | Cart    |
+-------------------------------------------------------------+
```

### دور الـ Reverse Proxy أثناء التطوير:
لمنع ظهور خطأ تقاطع الموارد المشتركة بين النطاقات (**CORS - Cross-Origin Resource Sharing**)، يقوم خادم التطوير Vite بالعمل كوكيل:
1. يرسل المتصفح الطلب إلى `http://localhost:5173/api/v1/products`.
2. يستقبل Vite الطلب وينقله داخلياً إلى خادم ASP.NET المستمع على `http://localhost:5097/api/v1/products`.
3. بهذه الطريقة يعتقد المتصفح أن الطلب يتجه لنفس النطاق، فلا تحدث أي مشاكل أمنية أو حظر لطلبات الـ API.

## 4. جدول الـ API Endpoints التي تم ربطها

تم فحص ومطابقة جميع الـ Endpoints التالية مباشرة من ملفات الـ Controllers في مشروع الباك إند:

### أولاً: وحدة المستخدمين والمصادقة (`Users.Module`)
| HTTP Method | المسار (Route) | صلاحية الوصول | مدخلات الطلب (Request Body) | الاستجابة (Response) | الهدف في الواجهة |
|:---:|:---|:---:|:---|:---|:---|
| `POST` | `/api/v1/users/register` | عام | `{ fullName, email, password }` | `{ accessToken, refreshToken, expiresAtUtc, user }` | إنشاء حساب جديد في شاشة التسجيل |
| `POST` | `/api/v1/users/login` | عام (محدد السرعة Rate Limited) | `{ email, password }` | `{ accessToken, refreshToken, expiresAtUtc, user }` | تسجيل الدخول وتخزين التوكن |
| `GET` | `/api/v1/users/me` | مسجل دخول (`[Authorize]`) | بدون | `{ id, fullName, email, role }` | التحقق من صحة الجلسة وتحديث بيانات المستخدم |
| `POST` | `/api/v1/users/logout` | عام | `{ refreshToken }` | `204 No Content` | إلغاء رمز التحديث وتسجيل الخروج |
| `POST` | `/api/v1/users/refresh` | عام | `{ refreshToken }` | `{ accessToken, refreshToken, ... }` | تجديد صلاحية الدخول عند انتهاء Access Token |

### ثانياً: وحدة التصنيفات (`Catalog / Products.Module`)
| HTTP Method | المسار (Route) | صلاحية الوصول | مدخلات الطلب | الاستجابة | الهدف في الواجهة |
|:---:|:---|:---:|:---|:---|:---|
| `GET` | `/api/v1/categories` | عام | بدون | `[ { id, name, description, imageUrl, ... } ]` | جلب التصنيفات لتصفية شاشة المنتجات واختيارها عند الإضافة |
| `POST` | `/api/v1/categories` | عام / Admin | `{ name, description, imageUrl, parentId }` | الكائن المنشأ مع معرفه `Id` | إمكانية إضافة تصنيف جديد مباشرة من شاشة إضافة المنتج |
| `PUT` | `/api/v1/categories/{id}` | عام / Admin | `{ name, description, imageUrl, parentId }` | الكائن المعدل | تحديث بيانات تصنيف قائم |
| `DELETE` | `/api/v1/categories/{id}` | عام / Admin | بدون | `204 No Content` | حذف تصنيف |

### ثالثاً: وحدة المنتجات (`Products.Module`)
| HTTP Method | المسار (Route) | صلاحية الوصول | مدخلات الطلب | الاستجابة | الهدف في الواجهة |
|:---:|:---|:---:|:---|:---|:---|
| `GET` | `/api/v1/products` | عام | Query Params: `pageNumber, pageSize, searchTerm, categoryId` | `PagedResult<ProductListDto>`: `{ items, pageNumber, pageSize, totalCount, totalPages }` | عرض بطاقات المنتجات مع البحث وتصفية الفئات وترقيم الصفحات |

| `DELETE` | `/api/v1/products/{id}` | عام / Admin | بدون | `204 No Content` | إزالة منتج من المتجر |

### رابعاً: وحدة الطلبات (`Orders.Module`)
| HTTP Method | المسار (Route) | صلاحية الوصول | مدخلات الطلب | الاستجابة | الهدف في الواجهة |
|:---:|:---|:---:|:---|:---|:---|

| `POST` | `/api/v1/orders` | زبون فقط (`Role: Customer`) | `{ items: [ { productId, quantity } ] }` | `OrderDto` مع تفاصيل الحجز والمجموع والحالة | إنشاء طلب جديد فور الضغط على تأكيد في صفحة Checkout |

| `GET` | `/api/v1/orders/{id}` | مسجل دخول (صاحب الطلب أو مدير) | بدون | `OrderDto` مع بنود المنتجات وتفاصيل الشراء | استعراض الفاتورة وتفاصيل الطلب |
| `PATCH` | `/api/v1/orders/{id}/status` | مدير فقط (`Role: Admin`) | `{ status: "Confirmed" \| "Shipped" \| ... }` | `OrderDto` المحدث | تغيير حالة الطلب من القائمة المنسدلة في شاشة المدير |

| HTTP Method | المسار (Route) | صلاحية الوصول | مدخلات الطلب | الاستجابة | الهدف في الواجهة |
|:---:|:---|:---:|:---|:---|:---|
| `GET` | `/api/v1/notifications` | مسجل دخول | بدون | مصفوفة: `[ { id, message, createdAt } ]` | جلب إشعارات المستخدم الحالية وعرضها |

## 5. كيف تعمل منظومة المصادقة والصلاحيات؟

تعتمد المنظومة على **JSON Web Tokens (JWT)** كمعيار أمان قياسي:

1. **تسجيل الدخول / إنشاء الحساب:**
   - يرسل المستخدم بياناته إلى مسار تسجيل الدخول أو التسجيل.
   - يعيد الباك إند استجابة تحتوي على:
     - `accessToken`: الرمز الأساسي الموقع بـ `HMAC-SHA256` ويحمل ادعاءات المستخدم (`NameIdentifier`, `Role`, `Email`).
     - `refreshToken`: رمز طويل الأمد لتجديد الجلسة.
     - `user`: كائن تفاصيل المستخدم (`Id`, `FullName`, `Email`, `Role`).

2. **التخزين الآمن في المتصفح:**
   - يتم تخزين `shopflow_token` و `shopflow_refresh_token` و `shopflow_user` في `localStorage` عبر وحدة `storage.js`.

3. **حقن التوكن الآلي (Request Interceptor):**
   - قبل خروج أي طلب من خلال كائن `http` (Axios)، يتم فحص وجود التوكن، وإذا وُجد يتم حقنه تلقائياً في الترويسة:
     ```http
     Authorization: Bearer <JWT_ACCESS_TOKEN>
     ```

4. **التحقق من انتهاء الصلاحية ومعالجة الخطأ 401:**
   - إذا انتهت صلاحية التوكن أثناء تصفح الصفحات المحمية وتلقى التطبيق استجابة `401 Unauthorized`، يقوم معترض الاستجابات بمحو بيانات الجلسة من التخزين المحلي فوراً وإعادة التوجيه لصفحة تسجيل الدخول بأمان.
   - تم استثناء شاشات الدخول والتسجيل من هذا السلوك لضمان بقاء رسالة "كلمة المرور غير صحيحة" ظاهرة للمستخدم دون إعادة تحميل الشاشة.

5. **فصل الأدوار (Role-Based Access Control - RBAC):**
   - يدعم النظام دورين رئيسيين: `Admin` (المدير) و `Customer` (الزبون).
   - المكون `ProtectedRoute` في الواجهة يتحقق من مصفوفة `allowedRoles`:
     - مسار `/checkout`: متاح للزبائن فقط (`Customer`).
     - مسار `/products/new`: متاح للمديرين فقط (`Admin`).
     - تتبدل عناصر شريط التصفح (Sidebar) ديناميكياً بحسب صلاحيات المستخدم المسجل.

## 6. طريقة تشغيل المشروعين واختبار الاتصال محلياً

### الخطوة الأولى: تشغيل الـ Backend
1. تأكد من تشغيل قواعد البيانات وخدمات Docker المطلوبة:
   ```bash
   docker compose up -d
   ```
   *(يقوم بتشغيل قاعدة بيانات Postgres لخدمات التطبيق، وقاعدة بيانات المستودع، وخدمة المستودع Java gRPC).*

2. الانتقال إلى مجلد استضافة تطبيق الـ .NET وتشغيله:
   ```bash
   cd src/AppService/AppService.Host
   dotnet run --launch-profile http
   ```
   *سيبدأ الخادم بالاستماع على: `http://localhost:5097`*
   *يمكنك التأكد من تشغيله عبر فتح واجهة توثيق Swagger في المتصفح: `http://localhost:5097/swagger`*

### الخطوة الثانية: تشغيل الواجهة الأمامية (Frontend)
1. الانتقال إلى مجلد الواجهة:
   ```bash
   cd c:\Users\Heba2005\Desktop\frontend
   ```
2. تثبيت الحزم (إن لم تكن مثبتة):
   ```bash
   npm install
   ```
3. تشغيل خادم التطوير:
   ```bash
   npm run dev
   ```
   *سيعمل الموقع محلياً على: `http://localhost:5173`*

### الخطوة الثالثة: اختبار السيناريوهات في المتصفح
1. **اختبار التسجيل والدخول:**
   - افتح المتصفح على `http://localhost:5173/register`.
   - أنشئ حساباً جديداً باسم (مثلاً: `Ahmad Ali`، إيميل: `ahmad@example.com`، كلمة مرور من 8 خانات: `password123`).
   - افتح أدوات المطور (F12) وانظر لتبويب **Network**: ستجد طلب `POST /api/v1/users/register` أعاد كود `201 Created`، ونقلك الموقع مباشرة إلى صفحة المنتجات.
2. **اختبار تصفح المنتجات:**
   - ستظهر لك المنتجات الحقيقية المسجلة في الباك إند مع أسعارها وتصنيفاتها.
   - جرّب البحث أو التصفية بحسب التصنيف لترى طلب `GET /api/v1/products?searchTerm=...` يعمل بسلاسة.
3. **اختبار الشراء وعملية الطلب:**
   - اضغط على أي منتج متوفر، أضفه إلى السلة، ثم توجه إلى شاشة الشراء `/checkout`.
   - اضغط على "Place order": سيتم استدعاء `POST /api/v1/orders` وتحويلك مباشرة إلى صفحة تفاصيل الطلب التي تعرض رقم الطلب الفعلي والمبلغ المحسوب من قاعدة البيانات.

## 7. أبرز المشاكل والتحديات التي واجهتنا وكيف حللناها

### 1. مشكلة وميض الشاشة وإعادة التحميل عند خطأ تسجيل الدخول:
* **المشكلة:** المعترض القديم في `api.js` كان مبرمجاً على محو الجلسة واستدعاء `window.location.assign("/login")` عند تلقي أي كود `401`. حين كان المستخدم يدخل بريداً أو كلمة سر خاطئة، كان الباك إند يعيد `401 INVALID_CREDENTIALS`، مما يدفع الصفحة لإعادة تحميل نفسها في نفس اللحظة فتختفي رسالة الخطأ قبل أن تقرأها المستخدمة!
* **الحل:** قمنا بتعديل المعترض ليفحص رابط الطلب؛ فإذا كان الطلب هو مسار تسجيل الدخول أو التسجيل نفسه، يتم تجاوز إعادة التوجيه وترك الواجهة تعرض الرسالة النصية التنبيهية باللون الأحمر بشكل طبيعي.

### 2. اختلاف تنسيقات رسائل الخطأ في الباك إند:
* **المشكلة:** بعض الخدمات في الباك إند تعيد `{ message: "..." }`، وبعض وحدات الـ Products تعيد `{ error: "..." }`، بينما تعيد أخطاء التحقق القياسية من ASP.NET كائن `{ errors: { FieldName: [...] } }`.
* **الحل:** بنينا منطق استخراج مرن وذكي في كلاس `ApiError`، بحيث يقرأ بالتتالي:
  `payload?.message || payload?.error || payload?.title || FALLBACK[status]`
  مع استخلاص كافة بنود `details` و `errors` ودمجها في رسالة واحدة مفهومة وواضحة للمستخدم.

### 3. استجابة إنشاء المنتج تعيد المعرف فقط:
* **المشكلة:** عند إرسال طلب `POST /api/v1/products` لإضافة منتج جديد، يعيد الباك إند استجابة من سطر واحد تحتوي على `{ id: "guid" }` ولا يعيد بيانات المنتج كاملة. كانت الواجهة تحاول قراءة الاسم والصورة فوراً مما يتسبب في أخطاء عرض.
* **الحل:** جعلنا دالة `addProduct` في `storeApi.js` تستخرج المعرف المنشأ `id` وتستدعي تلقائياً `getProduct(id)` لتعود الواجهة بكامل بيانات المنتج وتفاصيله المحدثة بكل ثقة.

### 4. عدم وجود حالة القراءة للإشعارات في الباك إند:
* **المشكلة:** نموذج الإشعار في الباك إند `NotificationDto` يحتوي فقط على المعرف والرسالة وتاريخ الإنشاء، ولا يملك حقلاً لمعرفة ما إذا كان الإشعار مقروءاً (`isRead`)، كما لا يوجد Endpoint لتعديل القراءة.
* **الحل:** لتجنب كسر وظيفة "Mark as read" و "Mark all as read" الممتازة في الواجهة، قمنا بحفظ قائمة معرفات الإشعارات المقروءة محلياً في المتصفح عبر `localStorage` ودمجها ديناميكياً مع استجابة الباك إند.

## 8. الوظائف التي لم تكتمل بعد ولماذا؟

1. **حالة قراءة الإشعارات على السيرفر:**
   - *السبب:* الباك إند لا يحتوي على عمود لقراءة الإشعارات في قاعدة البيانات حالياً. تعمل الميزة في الواجهة اعتماداً على المتصفح حتى يتم تزويد الباك إند بجدول/حقل القراءة.
2. **ربط المخزون الأولي عند إنشاء المنتج (`initialQuantity`):**
   - *السبب:* كائن `CreateProductRequest` في الباك إند يقبل فقط (الاسم، الوصف، السعر، التصنيف، الصور) ولا يتضمن كمية المخزون الأولية لأن إدارة المخزون مفصولة في خدمة المستودع Java gRPC، ولم يتم ربط أمر الحفظ الأولي بينهما بعد.

## 9. التعديلات المطلوبة والمقترحة في الـ Backend

> **ملاحظة:** تنفيذاً لتعليماتك، **لم يتم لمس أو تعديل أي ملف في الباك إند** من طرفنا، وهذه المقترحات مخصصة لتقومي بها أو لمشاركتها مع فريق الباك إند:

1. **تحديث عقد الإشعارات (`Notifications.Module`):**
   - إضافة خاصية `bool IsRead { get; set; }` إلى كيان الإشعار ونموذج `NotificationDto`.
   - إضافة Endpoint جديد:
     ```http
     PATCH /api/v1/notifications/{id}/read
     ```
2. **استقبال المخزون الأولي في إضافة المنتج (`Products.Module`):**
   - إضافة خاصية `int? InitialQuantity` إلى `CreateProductRequest`.
   - عند إنشاء المنتج بنجاح، يتم إطلاق حدث تكاملي (Integration Event) أو استدعاء خدمة `IWarehouseService` لتسجيل الرصيد الأولي في مستودع الجافا.
3. **توحيد نسق كائنات الخطأ:**
   - توحيد جميع الاستجابات غير الناجحة في الـ Controllers لتستخدم كائن `ApiError` نفسه (`{ code, message, details }`) بدلاً من إعادة `{ error = "..." }` في بعض الدوال.
