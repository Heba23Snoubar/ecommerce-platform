# سيناريو عرض المتطلب الخامس (T5-2)
 
## 1. هدف العرض

يهدف هذا العرض إلى توضيح كيفية توزيع الطلبات على عدة نسخ من التطبيق باستخدام Nginx، والتحقق من قدرة النظام على الاستمرار في معالجة الطلبات عند توقف إحدى النسخ ثم استعادتها.

يعتمد العرض على اختبارين رئيسيين:

- **T2:** اختبار إرسال 500 طلب ومقارنة النتائج قبل استخدام موازن الحمل وبعده.
- **T3:** اختبار استمرارية الخدمة أثناء إيقاف النسخة الثانية من التطبيق ثم إعادة تشغيلها.

---

## 2. الجزء الأول: اختبار توزيع الحمل (T2)

### الهدف

التحقق من أن النظام يستطيع معالجة 500 طلب بنجاح، وأن الطلبات تمر عبر Nginx عند استخدام موازن الحمل.

### إعداد الاختبار

- الأداة المستخدمة: k6.
- عدد المستخدمين الافتراضيين: 10.
- إجمالي الطلبات: 500.
- نوع الطلب: GET.
- المسار:
  `/api/v1/orders?page=1&pageSize=50`

أُجري الاختبار في حالتين:

1. **Baseline:** قبل استخدام موازن الحمل.
2. **Load Balanced:** بعد تمرير الطلبات عبر Nginx.

### النتائج

| المؤشر | قبل موازن الحمل | بعد موازن الحمل |
|---|---:|---:|
| عدد الطلبات | 500 | 500 |
| متوسط معدل الطلبات (req/s) | 328.94 | 181.96 |
| Median | 15.63 ms | 34.78 ms |
| P90 | 28.67 ms | 69.21 ms |
| P95 | 42.82 ms | 89.99 ms |
| P99 | 589.72 ms | 556.70 ms |
| عدد الاختبارات الناجحة (Checks) | 1000 | 1000 |
| عدد الاختبارات الفاشلة (Checks) | 0 | 0 |

### ماذا نعرض أثناء المناقشة؟

1. فتح ملف `tests/performance/orders-load.js`.
2. توضيح أن الاختبار يرسل 500 طلب إلى Orders API باستخدام 10 مستخدمين افتراضيين.
3. عرض نتائج الاختبار قبل موازن الحمل وبعده.
4. توضيح أن الاختبار يتحقق من أمرين:
   - استجابة Orders API برمز HTTP 200.
   - وجود ترويسة `X-Served-By` التي تساعدنا على معرفة النسخة التي عالجت الطلب.
5. عرض ملفات النتائج الموجودة في:
   `tests/performance/results/`

### الاستنتاج

نجح الاختبار في الحالتين، حيث عولجت الطلبات الـ500 دون فشل في الاختبارات المسجلة.

لكن أرقام الأداء لا تثبت تحسن السرعة بعد إضافة Nginx؛ فقد كان معدل الطلبات أقل وزمن الاستجابة P95 أعلى في الاختبار الثاني.

لذلك، هدف هذا الاختبار هو التحقق من عمل النظام خلف موازن الحمل وصحة الاستجابات، وليس الادعاء بأن إضافة Nginx حسّنت سرعة الاستجابة.

## 3. الجزء الثاني: اختبار توقف نسخة واستعادتها (T3)

### الهدف

التحقق من سلوك النظام عند توقف إحدى نسخ التطبيق أثناء استمرار إرسال الطلبات، ثم التأكد من عودة النسخة للعمل بعد إعادة تشغيلها.

### إعداد الاختبار

- الأداة المستخدمة: k6.
- عدد المستخدمين الافتراضيين: 10.
- مدة الاختبار: 90 ثانية.
- إجمالي الطلبات المسجلة: 23,144.
- نوع الطلب: GET.
- المسار:
  `/api/v1/orders?page=1&pageSize=50`

### خطوات تنفيذ السيناريو

1. تشغيل اختبار T3 مع استمرار إرسال الطلبات إلى Orders API عبر Nginx.
2. إيقاف النسخة الثانية `app2` أثناء استمرار الاختبار.
3. مراقبة الطلبات والنسخ التي تستمر في معالجة الطلبات.
4. إعادة تشغيل `app2`.
5. التأكد من عودة النسخة إلى العمل واستقبالها للطلبات.

### أوقات الأحداث المسجلة

| الحدث | الوقت |
|---|---|
| طلب إيقاف app2 | 20:49:08 |
| تأكيد توقف app2 | 20:49:14 |
| طلب إعادة تشغيل app2 | 20:49:44 |
| تأكيد تشغيل app2 | 20:49:49 |

التاريخ: 24 نوفمبر 2026.

### النتائج

| المؤشر | النتيجة |
|---|---:|
| إجمالي الطلبات | 23,144 |
| الطلبات الناجحة وفق HTTP 200 | 23,135 |
| الطلبات الفاشلة وفق HTTP 200 Check | 9 |
| نسبة الفشل | 0.039% تقريبًا |
| Median | 25.88 ms |
| P90 | 53.45 ms |
| P95 | 68.57 ms |
| P99 | 135.60 ms تقريبًا |

### ملاحظات مهمة

- استمرت النسختان `app1` و`app3` في معالجة الطلبات أثناء توقف `app2`.
- سُجلت خمسة إخفاقات أثناء فترة توقف النسخة.
- سُجل إجمالي تسعة إخفاقات خلال الاختبار، لذلك لا يمكن الادعاء بأن الخدمة استمرت دون أي انقطاع.
- بعد استعادة `app2`، أُرسلت 30 طلب GET إضافيًا للتحقق من عودتها.
- نجحت الطلبات الثلاثون جميعها برمز HTTP 200.
- توزعت الطلبات الإضافية بالتساوي: 10 طلبات لكل نسخة من النسخ الثلاث.
- الاختبار استخدم طلبات قراءة فقط، ولم يتضمن إنشاء طلبات شراء جديدة.

### ماذا نعرض أثناء المناقشة؟

1. فتح `tests/performance/orders-resilience.js`.
2. شرح إعداد الاختبار: 10 مستخدمين افتراضيين لمدة 90 ثانية.
3. عرض ملف `t3-events.log` لتوضيح توقيت إيقاف النسخة واستعادتها.
4. عرض `t3-summary.json` لتوضيح عدد الطلبات الناجحة والفاشلة.
5. عرض `t3-run.log` لمراجعة الأحداث والنتائج المسجلة.
6. توضيح نجاح الطلبات الثلاثين بعد استعادة النسخة وتوزعها على النسخ الثلاث.

### الاستنتاج

أظهر الاختبار قدرة النسخ الأخرى على مواصلة معالجة معظم الطلبات أثناء توقف `app2`، كما أثبت نجاح استعادة النسخة وعودتها إلى استقبال الطلبات.

ومع ذلك، سُجلت تسعة إخفاقات قصيرة أثناء الاختبار، ولذلك فإن النظام أظهر قدرة على التعافي وتقليل أثر توقف النسخة، وليس استمرارية كاملة دون أي إخفاق.

## 4. الجزء الثالث: عرض مشكلات الفريق قبل الإصلاح وبعده

**هذا القسم مؤجل مؤقتًا حتى اكتمال مهام S ووصول أدلة الفريق.**

سيُضاف لكل مشكلة:

- وصف المشكلة قبل الإصلاح.
- سبب حدوثها.
- التعديل الذي عالج المشكلة.
- الدليل قبل الإصلاح.
- الدليل بعد الإصلاح.
- النتيجة التي تثبت نجاح المعالجة.

لن تُضاف نتائج أو استنتاجات قبل استلام الأدلة الفعلية.

---

## 5. الخلاصة النهائية للعرض

من خلال الاختبارين T2 وT3، تحققنا من النقاط التالية:

1. معالجة 500 طلب بنجاح قبل استخدام Nginx وبعده.
2. تمرير الطلبات عبر موازن الحمل والتحقق من وجود `X-Served-By`.
3. استمرار النسخ الأخرى في معالجة الطلبات عند توقف إحدى النسخ.
4. استعادة النسخة المتوقفة والتحقق من عودتها لاستقبال الطلبات.
5. تسجيل وتحليل الطلبات الناجحة والفاشلة بدل الاكتفاء بالقول إن النظام يعمل.

**النتيجة:** أظهرت الاختبارات أن النظام يدعم توزيع الحمل والتعافي من توقف إحدى النسخ، مع وجود إخفاقات محدودة أثناء سيناريو التوقف والاستعادة، وهي نتائج يجب توضيحها بأمانة أثناء المناقشة.
