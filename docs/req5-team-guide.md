# المتطلب الخامس: التوسع وتوزيع الأحمال



## 1. المطلوب بالضبط

الهدف: تشغيل النظام على **أكثر من نسخة** في وقت واحد **دون أن يلاحظ المستخدم أي فرق**. لا ميزات جديدة، بل نأخذ ما بنيناه في المتطلبات الأربعة ونشغّله على ثلاث نسخ.

| المطلوب | التفصيل |
|---|---|
| توسع أفقي | ثلاث نسخ متطابقة من AppService، وموزّع حمل (Nginx) هو الباب الوحيد |
| خدمات مشتركة | PostgreSQL وRedis وRabbitMQ وWarehouse وSoketi مشتركة بين النسخ |
| استراتيجية التوزيع | نختار واحدة (IP Hash أو Least Connections أو Round Robin) **ونبرّر**، ونجيب: ما عيب ربط العميل بنسخة واحدة؟ |
| ثلاثة عمّال | على الطابور نفسه، **كل رسالة يأخذها عامل واحد**، والمطلوب بريد واحد لكل طلب |
| الاستمرارية | إيقاف نسخة لا يوقف النظام، والموزّع يحوّل الطلبات للباقيتين |
| المشاكل الخفية | نشغّل ثلاث نسخ ونفحص **كل ميزة** بحثاً عن كل ما يُحفظ **في ذاكرة النسخة أو ملفاتها أو قرصها** |

**الشرط الذهبي:** أي نسخة يجب أن تستطيع خدمة أي طلب.

**الإثبات المطلوب في المقابلة:**
1. اختبار حمل **500 طلب** يتوزع على النسخ الثلاث.
2. إيقاف نسخة أثناء الاختبار: النظام يستمر بأخطاء قليلة جداً أو بلا أخطاء.
3. **كل مشكلة وجدناها: قبل الإصلاح وبعده** (ماذا حدث؟ لماذا؟ كيف أصلحناها؟). الاكتشاف جزء من المتطلب، وهو أكثر ما يُحاسَب عليه.

## 2. المعمارية النهائية

```
                        المتصفح
                   │              │
        REST /api  │              │  WebSocket (مباشرة)
                   ▼              ▼
            ┌───────────┐   ┌───────────┐
            │  Nginx    │   │  Soketi   │  ← مشترك، يستقبل البث من أي نسخة
            │  :8088    │   │  :6001    │
            └─────┬─────┘   └───────────┘
        least_conn│
      ┌───────────┼───────────┐
      ▼           ▼           ▼
   ┌──────┐   ┌──────┐   ┌──────┐
   │ app1 │   │ app2 │   │ app3 │      ثلاث نسخ متطابقة (JWT_KEY نفسه)
   └──┬───┘   └──┬───┘   └──┬───┘
      └──────────┼──────────┘
        ┌────────┼─────────┬──────────┬───────────┐
        ▼        ▼         ▼          ▼           ▼
   PostgreSQL  Redis    RabbitMQ   Warehouse   (replica)
   (primary)  (cache +  (طابور     (gRPC)
              علامات)    orders.email)
                              │
                 ┌────────────┼────────────┐
                 ▼            ▼            ▼
            order-worker ×3  (نفس الطابور، Redis للـ idempotency)
```

| الخدمة | الدور | ملاحظة |
|---|---|---|
| `nginx` | الموزّع الوحيد | المنفذ 8088 على الجهاز |
| `app1` و`app2` و`app3` | AppService | صورة واحدة بثلاثة أسماء، لكل منها خدمة |
| `order-worker` | يرسل البريد | يُشغَّل بثلاث نسخ: `--scale order-worker=3` |
| `redis` | كاش + علامة الكتابة + مخزن الـ idempotency | مشترك |
| `rabbitmq` | طابور `orders.email` وDLQ | مشترك |
| `soketi` | WebSocket | المتصفح يتصل به مباشرة لا عبر Nginx |
| `app-db` و`app-db-replica` | قاعدة الكتابة وقاعدة القراءة | تراجع القسم 4 (S6) |

**لماذا ثلاث خدمات صريحة (`app1/2/3`) وليس `--scale app=3`؟** (1) Nginx يحتاج أسماء ثابتة في `upstream`. (2) نستطيع إيقاف نسخة **بعينها** في اختبار الاستمرارية. (3) نتحكم بترتيب الإقلاع (نسخة أولى ثم البقية).

## 3. كيف نفّذنا كل جزء

### 3.1 الحاويات الثلاث (I1: أ)
- صورة AppService واحدة، وثلاث خدمات تستعملها بكتلة إعدادات مشتركة (YAML anchor).
- داخل Docker كلمة `localhost` تعني **الحاوية نفسها**، لذلك كل عناوين `appsettings.json` استُبدلت بأسماء الخدمات (`app-db` و`redis` و`warehouse` و`rabbitmq` و`soketi`) عبر متغيرات بيئة.
- **`JWT_KEY` و`JWT_ISSUER` و`JWT_AUDIENCE` متطابقة في النسخ الثلاث.** لو اختلف المفتاح لرفضت نسخةٌ توكناً وقّعته نسخة أخرى فيظهر 401 متقطع. وهو اختبار نجح: نسجّل الدخول على نسخة ونستعمل التوكن على الأخرى.
- لم ننشر منافذ للمضيف لكل نسخة: الباب الوحيد هو Nginx.

### 3.2 موزّع الحمل Nginx (I2: أ)

```nginx
upstream appservice_backend {
    least_conn;
    server app1:8080 max_fails=2 fail_timeout=10s;
    server app2:8080 max_fails=2 fail_timeout=10s;
    server app3:8080 max_fails=2 fail_timeout=10s;
}
proxy_connect_timeout 2s;
proxy_next_upstream error timeout http_502 http_503 http_504;
proxy_next_upstream_tries 3;
```

| الإعداد | لماذا |
|---|---|
| `least_conn` | يرسل الطلب إلى النسخة ذات الاتصالات النشطة الأقل: كلفة الطلبات متفاوتة (إنشاء طلب أثقل بكثير من قراءة منتج مخزّنة) |
| `max_fails=2 fail_timeout=10s` | مراقبة سلبية: بعد فشلين خلال 10 ثوانٍ يتجنب Nginx النسخة 10 ثوانٍ ثم يجرّبها بطلب واحد |
| `proxy_connect_timeout 2s` | الافتراضي 60 ثانية، وبدونه ينتظر أول طلبات بعد توقف نسخة دقيقة كاملة |
| `proxy_next_upstream` | الطلب الذي فشل **اتصاله** يُعاد على نسخة أخرى فلا يرى العميل الخطأ |
| لا `non_idempotent` عمداً | حتى لا يُعاد طلب `POST` أُرسل فعلاً فيتكرر الطلب |
| `worker_connections 4096` | الافتراضي 512، وكل اتصال عميل يستهلك اتصالاً آخر نحو النسخة، فيصير الموزّع هو الاختناق |
| `X-Forwarded-For` و`X-Forwarded-Proto` و`Host` | ليعرف التطبيق العميل الحقيقي |
| ترويسة `X-Upstream` وسجل `upstream=` | **دليل**: أي نسخة خدمت كل طلب |

**قيد نذكره بصدق:** Nginx يحلّ أسماء النسخ **عند إقلاعه فقط**، فإن تغيّر عنوان حاوية بعد إعادة تشغيلها قد نحتاج `docker compose restart nginx`.

### 3.3 العمّال الثلاثة (W1 وW2 وW3: ب)
- ثلاث نسخ من `order-worker` على **الطابور نفسه** (competing consumers) و`prefetch=1`: كل رسالة تذهب لعامل واحد.
- **الـ idempotency في Redis** (كان ملفاً محلياً لكل عامل، فلا يعرف عاملٌ ما أرسله آخر).
- **مفتاحان وليس مفتاحاً واحداً:**
  - `lock:{orderId}`: حجز مؤقت (lease) أثناء المعالجة، **ينتهي وحده** إن مات العامل.
  - `sent:{orderId}`: علامة نهائية **تُكتب بعد نجاح الإرسال فقط**.
- رسالة أُعيدت وحجزها عند عامل ميت لم ينتهِ بعد: **تُعاد إلى الطابور** (`nack requeue`) بدل أن تُهمل، حتى ينتهي الحجز فتُعالَج.
- إعادة محاولة 3 مرات (تأخير 2 ثم 4 ثوانٍ) ثم `reject` إلى `orders.email.dlq`.
- **للاختبار فقط:** `EMAIL_SENDER=fake` يعدّ كل «إرسال» في Redis ولا يرسل بريداً حقيقياً (500 بريد حقيقي إلى Gmail كانت ستُقيّد الحساب).

### 3.4 إصلاح الحالة المحلية (ج وب)
تفصيلها في القسم 4: علامة الكتابة، ومحدّد الدخول، وmigrations، ومسبح الاتصالات، وفحص الـ replica.

### 3.5 الإثبات (د والكل)
- `load-500.ps1`: 500 طلب بعدة خيوط عبر الموزّع، ويطبع نسبة النجاح وزمن الاستجابة **وتوزيع الطلبات على النسخ** وتناسق القراءة.
- `-StopService app2`: يوقف نسخة وسط الاختبار.
- `w3-verify.ps1`: بريد واحد لكل طلب مع ثلاثة عمّال.

## 9. أسئلة المقابلة وأجوبة نموذجية

### الموزّع والتوزيع

1. **ما التوسع الأفقي وما الفرق عن العمودي؟** الأفقي إضافة نسخ متطابقة من الخدمة خلف موزّع، والعمودي تكبير جهاز واحد. الأفقي يتجاوز حد الجهاز الواحد ويتحمل فشل نسخة، لكنه يتطلب أن تكون النسخ **بلا حالة محلية**.
2. **لماذا Least Connections؟** كلفة الطلبات متفاوتة: إنشاء طلب يمرّ بالقاعدة وgRPC وRabbitMQ والبث، وهو أثقل من قراءة مخزّنة في Redis. Round Robin يوزّع بعدد الطلبات، أما Least Connections فيقرّب توزيع الحمل الفعلي، ويخفف عن النسخة البطيئة تلقائياً.
3. **ما عيب ربط العميل بنسخة واحدة (IP Hash)؟** يختل التوازن (مستخدمون خلف NAT يظهرون بعنوان واحد)، وتصير النسخة نقطة فشل لمن ارتبط بها، ويُخفي أخطاء الحالة المحلية فتبدو سليمة حتى يحدث توزيع حقيقي، ويعيق التوسع والصيانة. نحن أصلحنا الأصل بدل إخفائه.
4. **لماذا نتيجة 12 طلباً متتالياً متساوية تماماً (4/4/4)؟** مع طلبات متتالية تتساوى الاتصالات النشطة، فيتصرف `least_conn` كـ Round Robin. يظهر الفرق الحقيقي تحت حمل متزامن.
5. **ماذا يحدث لو توقفت نسخة؟** الطلبات الجديدة تتحول للباقيتين: Nginx يكتشف فشل الاتصال (مهلة 2 ثانية) ويعيد الطلب على نسخة أخرى، وبعد فشلين خلال 10 ثوانٍ يتجنبها 10 ثوانٍ.
6. **هل يضيع أي طلب عند توقف نسخة؟** قد يفشل **الطلب الذي كان قيد المعالجة لحظة التوقف**، ولا نعيد `POST` تلقائياً لأن ذلك قد يكرر الطلب. أما الطلبات الجديدة فلا تفشل.
7. **ماذا لو توقف Nginx نفسه؟** هو نقطة فشل وحيدة في تصميمنا (حد معروف). الحل في الإنتاج: موزّعان مع عنوان افتراضي مشترك (مثل keepalived) أو موزّع سحابي مُدار.
8. **كيف يعرف Nginx أن النسخة عادت؟** بعد `fail_timeout` يجرّبها بطلب واحد. وهو يحلّ الأسماء عند الإقلاع فقط، فإن تغيّر عنوان حاوية قد نعيد تشغيله.
9. **كيف أثبتّم أن الطلبات تتوزع؟** ترويسة `X-Upstream` وسجل Nginx (`upstream=`) وسكربت `load-500.ps1` الذي يعدّ الطلبات الناجحة لكل نسخة بنسب مئوية.

### الحالة المشتركة

10. **ما الذي يجب أن يكون مشتركاً ليخدم أي نسخة أي طلب؟** كل حالة المستخدم: القاعدة وRedis وRabbitMQ، ومفتاح توقيع JWT نفسه، فلا يبقى شيء في ذاكرة النسخة أو قرصها.
11. **لماذا يعمل التوكن على كل النسخ؟** JWT بلا حالة موقَّع بـ `JWT_KEY` متطابق في النسخ، وكل نسخة تتحقق منه محلياً. لو اختلف المفتاح لظهر 401 متقطع.
12. **وماذا عن WebSocket؟** Soketi خدمة مشتركة، والتطبيق يبثّ إليه من أي نسخة، والمتصفح يتصل به مباشرة، فلا يتأثر بتوزيع REST.

### المشاكل الخفية

13. **اشرح أهم مشكلة وجدتموها.** S1: التطبيق يوجّه قراءة المستخدم إلى قاعدة الكتابة 5 ثوانٍ بعد كتابته (لأن الـ replica تتأخر). كانت العلامة في ذاكرة النسخة، فمن كتب على نسخة وقرأ من أخرى رأى بيانات قديمة. نقلناها إلى Redis فصارت مشتركة.
14. **لماذا Redis وليس IP Hash أو Sticky؟** لأنه يعالج السبب، ولا ينهار عند توقف نسخة أو تغيّر العنوان.
15. **وماذا لو توقف Redis؟** نقرأ من الـ primary، فلا نعرض بيانات قديمة، ونخسر فقط فائدة الـ replica مؤقتاً.
16. **لماذا كل المستخدمين يشتركون في حد تسجيل الدخول؟** المحدّد يعتمد على IP العميل، وخلف الموزّع يصل كل شيء بعنوان الموزّع. الحل أن يقرأ التطبيق `X-Forwarded-For` من **وكيل موثوق فقط** (وإلا تزوّر العميل هذه الترويسة).
17. **لماذا تتسابق migrations؟** كل نسخة تشغّلها عند الإقلاع، فتبدأ ثلاث نسخ معاً على قاعدة فارغة. نشغّلها مرة واحدة (نسخة أولى أو خدمة منفصلة) ثم نقلع الباقي.
18. **كم اتصالاً قد تفتح النسخ الثلاث؟** عدد الوحدات (مسبح لكل وحدة ودور) × حجم المسبح × عدد النسخ. بالحد الافتراضي 100 يتجاوز ذلك بكثير `max_connections=100`. حدّدنا حجم المسبح ورفعنا `max_connections`.
19. **لماذا نرفع `max_connections` على الـ replica أيضاً؟** الـ standby لا يبدأ إذا كان حدّه أقل من الـ primary.
20. **لماذا تُبطئ `Console.WriteLine` النظام؟** تُكتب بشكل متزامن عند كل طلب وتحت 500 طلب تتزاحم، ويصعب قراءة سجل ثلاث نسخ. استبدلناها بـ `ILogger` بمستوى Debug.
21. **لماذا كانت كل القراءات تذهب للـ primary؟** فحص صحة الـ replica يتجه إلى `localhost:5434`، وداخل Docker هي الحاوية نفسها. (حددوا: أصلحناها أو وثّقناها كحد.)

### العمّال

22. **كيف تضمنون بريداً واحداً مع ثلاثة عمّال؟** الطابور يسلّم كل رسالة لعامل واحد، وعلامة idempotency مشتركة في Redis بمفتاح `orderId` تمنع الإرسال مرتين حين تُعاد رسالة.
23. **ماذا لو مات عامل أثناء المعالجة؟** تعود الرسالة إلى الطابور (لم تُؤكَّد). حجزه المؤقت ينتهي وحده، فتُعالَج من عامل آخر وتُرسل مرة واحدة.
24. **لماذا لم تكفِ علامة واحدة تُكتب قبل الإرسال؟** لأن موت العامل بعدها يترك العلامة، فتُعاد الرسالة وتُعدّ «مكررة» فتُهمل ويضيع البريد (وجدناه باختبار: 11 بريداً لـ 12 طلباً). فصلنا الحجز المؤقت عن علامة «أُرسل» التي تُكتب بعد النجاح.
25. **هل يمكن أن يتكرر البريد؟** نعم في نافذة صغيرة: لو مات العامل بعد نجاح SMTP وقبل كتابة علامة «أُرسل». هذا طبيعي في أي نظام يرسل لخدمة خارجية (التسليم مرة على الأقل). نخفّفه ولا نلغيه إلا بمفتاح idempotency عند المزود.
26. **لماذا اختبرتم بإرسال وهمي؟** 500 بريد حقيقي إلى عناوين وهمية ترتدّ وتُقيّد الحساب، والإرسال الوهمي يعدّ كل إرسال في Redis فنثبت الأرقام بدقة.

### الاختبار والحدود

27. **ماذا نتج عن اختبار الـ 500 طلب؟** نقرأ الأرقام من القسم 5: عدد الطلبات الناجحة والإنتاجية وp95 والتوزيع على النسخ وتناسق القراءة. وما فشل نذكر سببه (مثلاً نفاد المخزون يعطي 409).
28. **ما عنق الزجاجة الآن؟** قاعدة PostgreSQL الوحيدة للكتابة، ثم Nginx وRedis وRabbitMQ كل منها نسخة واحدة. إضافة نسخ تطبيق لا تحلها، فنحتاج تقسيماً أو replicas للقراءة أو تجميعاً (cluster).
29. **لو زدنا النسخ إلى عشر؟** ينفد مسبح اتصالات القاعدة أولاً (لذلك حسبنا المسبح)، ثم يصير Nginx الواحد نقطة اختناق، ويجب تعديل `upstream` يدوياً.
30. **ما الفرق بين التوسع (scalability) والتوافر العالي (high availability)؟** التوسع قدرتنا على خدمة حمل أكبر بإضافة موارد، والتوافر العالي أن يستمر النظام عند فشل جزء منه. نغطي الثاني للنسخ والعمّال، ولا نغطيه لـ Nginx وPostgreSQL.
31. **كيف قسمتم العمل وتأكدتم من الجودة؟** أربعة أدوار (بنية، عمّال، حالة محلية، إثبات)، وبطاقة صغيرة لكل مهمة، وPR لكل مهمة بمراجعة زميل، ولا تُعدّ المهمة تامة إلا بعد الدمج والتجربة.

## 10. القيود المعروفة 

- **Nginx وحيد:** نقطة فشل واحدة، ويحلّ أسماء النسخ عند الإقلاع فقط.
- **PostgreSQL للكتابة واحد:** هو العنق الأول عند التوسع الكبير.
- **idempotency:** نافذة صغيرة بعد نجاح SMTP، وتتطلب مفتاح idempotency عند المزود لإلغائها.
- **DLQ بلا أداة إعادة معالجة** ولا تنبيه عند امتلائها.
- **محدّد الدخول:** ⟨الحد الموثّق: عدّاد لكل نسخة أم مشترك⟩.
- **فشل الطلب الجاري لحظة توقف نسخة** (لا نعيد `POST`).
- **المراقبة والأعطال:** هي المتطلب السادس، ولم نبنها هنا.

docker compose ps                                   # حالة الخدمات

docker compose up -d --no-build --scale order-worker=3 order-worker
docker compose stop app2 ; docker compose start app2

docker compose logs --tail 20 nginx                 # أي نسخة خدمت الطلبات (upstream=)
docker compose logs -f order-worker                 # سجل العمّال

docker compose exec app-db-replica psql -U postgres -d appdb -c "SELECT pg_wal_replay_resume();"
